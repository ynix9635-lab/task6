1. Почему sc create python.exe script.py даёт Error 1053?
SCM после запуска бинарника ждёт в течение ~30 секунд, 
что процесс вызовет StartServiceCtrlDispatcher и по RPC-каналу зарегистрирует функцию ServiceMain, 
а затем отчитается о статусе SERVICE_RUNNING через SetServiceStatus. 
Интерпретаторы python.exe/powershell.exe — обычные консольные приложения Ring 3, протокол SCM не знают, 
ServiceMain не вызывают и статус не сообщают. SCM решает, что служба зависла, и убивает процесс с ошибкой 1053.

2. Парадокс: PowerShell-задача работает в Сессии 0 от SYSTEM, но sc query её не видит.
Потому что она зарегистрирована не в базе SCM (HKLM\SYSTEM\CurrentControlSet\Services), 
а в подсистеме Планировщика заданий (Task Scheduler, Schedule service + хранилище заданий). 
Register-ScheduledJob создаёт задание в планировщике, который сам запускает процесс от имени SYSTEM в Сессии 0 при старте системы. 
Это отдельный механизм управления фоновыми процессами, работающий в обход SCM. sc.exe обращается только к SCM, 
поэтому службы с таким именем «не установлено» (ошибка 1060), хотя процесс реально работает.

3. Execution Policy и зачем менять на RemoteSigned.
Execution Policy — политика безопасности PowerShell, определяющая, 
какие скрипты (.ps1) разрешено выполнять (Restricted / AllSigned / RemoteSigned / Unrestricted / Bypass). 
По умолчанию на клиентских Windows часто стоит Restricted, 
и фоновый скрипт не запустится. RemoteSigned разрешает локальные скрипты без подписи, 
но требует подпись для скачанных из интернета. Риски: это не граница безопасности ядра (легко обходится через -ExecutionPolicy Bypass, Invoke-Expression и т.п.), 
но ослабление политики позволяет выполнять потенциально вредоносные локальные сценарии — растёт поверхность атаки на уровне Ring 3 (пользовательские процессы), 
хотя привилегии ядра не затрагиваются.

логический тупик: 

PowerShell-задача зарегистрирована не в SCM, 
а в Планировщике заданий (Task Scheduler). 
Это два независимых механизма управления фоновыми процессами:

SCM (sc.exe) управляет только службами из ветки реестра HKLM\SYSTEM\CurrentControlSet\Services. 
Python-обёртка регистрируется там через win32serviceutil → sc query PyBackgroundService её видит.

Планировщик заданий хранит свои задания в отдельном хранилище (C:\Windows\System32\Tasks + служба Schedule). 
Register-ScheduledJob создаёт задание именно там. 
Планировщик сам запускает процесс от имени SYSTEM в Сессии 0 при старте системы — поэтому скрипт реально работает и пишет логи, 
но для SCM это «посторонний» процесс, не зарегистрированный как служба.

Поэтому sc query PowerShellBackgroundMonitor возвращает ошибку 1060 «Указанная служба не установлена» — SCM просто не знает о существовании задания, 
потому что им управляет другая подсистема Windows.
